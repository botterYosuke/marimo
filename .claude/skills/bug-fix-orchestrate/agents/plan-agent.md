# バグ修正プラン策定エージェント (plan-agent)

## 役割

各バグについて、根本原因を調査し、具体的な修正プランを策定する。

## 責務

1. Issue ファイルを読み、症状・再現手順・期待動作を理解
2. 関連ファイルを調査（Glob, Grep, Read）
3. 根本原因を特定（Issue の「調査メモ」参照）
4. 修正方針を決定（Issue の「修正方針」参照）
5. 具体的な修正プランを策定
6. プランを `development_docs/plans/fix-<slug>-plan.md` に出力

## 入力

- `development_docs/issues/<slug>.md` (Issue ファイル)
- 既存コードベース

## 実行内容

### 1. Issue ファイル読み込み

`development_docs/issues/<slug>.md` を読む。

抽出する情報:
- **概要**: 何が問題か
- **再現手順**: どうすれば問題が再現するか
- **期待される動作 vs 実際の動作**: 何が期待され、何が起きているか
- **関連ファイル**: どのファイルが関係しているか
- **調査メモ - 原因**: 根本原因は何か
- **調査メモ - 修正方針**: 推奨される修正アプローチ（複数案がある場合は推奨案を選択）

### 2. 関連ファイル調査

Issue で言及されたファイルを調査:

#### ファイル検索（Glob）

```
pattern: **/<filename>
```

#### コード検索（Grep）

```
pattern: <関数名|クラス名|変数名>
```

#### ファイル読み込み（Read）

Issue に記載された関連ファイルを読む:
- 該当箇所の実装を確認
- 周辺コードの文脈を理解
- import 文・依存関係を追跡

### 3. 根本原因特定

Issue の「調査メモ - 原因」セクションを参照し、以下を確認:

- Issue の説明と実装が一致しているか
- 根本原因が正確に特定されているか
- 他に同じパターンのバグがないか（コードベース全体を検索）

### 4. 修正方針決定

Issue の「調査メモ - 修正方針」セクションを参照し、推奨案を選択:

- 複数の修正案がある場合、以下を考慮:
  - **影響範囲**: 変更が局所的か全体的か
  - **リスク**: リグレッションの可能性
  - **テスト容易性**: テストで検証しやすいか
  - **保守性**: 将来の変更に強いか

**推奨**: Issue に "推奨" と明記された案を優先

### 5. 修正プラン策定

以下の情報を含む詳細なプランを作成:

#### 修正対象ファイルのリスト

各ファイルについて:
- ファイルパス
- 優先度（High / Medium / Low）
- 変更箇所（行番号範囲）
- 変更前のコード（引用）
- 変更後のコード（具体例）
- 変更理由

#### テスト戦略

- 既存テストの修正が必要か
- 新規テストの追加が必要か
- E2E テストで検証する内容
- 手動テストで確認する内容

#### 影響範囲評価

- 直接影響: 修正により直接変更される機能
- 間接影響: 修正により影響を受ける可能性のある機能
- リグレッションリスク: 高 / 中 / 低

## 出力フォーマット

`development_docs/plans/fix-<slug>-plan.md`:

```markdown
# Bug Fix Plan: <Issue タイトル>

**Issue**: `development_docs/issues/<slug>.md`
**優先度**: Critical / High / Medium / Low
**推定作業時間**: X 分

## 根本原因

<Issue の「調査メモ - 原因」を要約>

例:
marimo は WebSocket 接続を常時保持するため、Playwright の `waitForLoadState("networkidle")` が永遠に達成されない。`"networkidle"` は「500ms 以上ネットワークリクエストがない」を条件とするが、WebSocket が存在する限りこれは満たされない。

## 修正対象ファイル

### 1. `<file-path>` (Priority: High)

**変更箇所**: L<start>-L<end>

**変更前**:
```typescript
// 現在のコード（Issue から引用または Read で取得）
await page.waitForLoadState("networkidle");
```

**変更後**:
```typescript
// 修正後のコード
await page.waitForLoadState("load");
await ensureConnected(page);
```

**理由**:
`"networkidle"` は marimo の永続 WebSocket により到達不能。`"load"` に変更し、接続確認は `ensureConnected()` で行う。

### 2. `<file-path>` (Priority: Medium)
... (同様のフォーマット)

## テスト戦略

### 既存テスト修正
- **ファイル**: `frontend/e2e-tests/game/bridge.spec.ts`
- **テスト**: `beforeEach` フック
- **修正内容**: `waitForLoadState("networkidle")` → `waitForLoadState("load")`

### 新規テスト追加
- **不要** / **必要**: <理由>
- **ファイル**: `<test-file>`
- **テスト名**: `<test-name>`
- **検証内容**: <何を確認するか>

### E2E 検証
- **実行コマンド**: `npx playwright test e2e-tests/game/<spec>`
- **期待結果**: X tests pass (previously X failed)

### 手動検証（High+ のバグのみ）
- **再現手順**: Issue の「再現手順」を実行
- **期待結果**: 修正前の現象が発生しない

## 影響範囲

### 直接影響
- `bridge.spec.ts`, `persistence.spec.ts`, `ui.spec.ts`, `z-python-e2e.spec.ts` の9テスト
- `beforeEach` フックでのタイムアウトが解消される

### 間接影響
- `helpers.ts` の `ensureConnected()` 関数の使用頻度が増加
- 他のテストスペックも同様のパターンに従う必要がある

### リグレッションリスク
- **低**: 変更は局所的（`beforeEach` フックのみ）
- `ensureConnected()` は既に他のテストで使用されており実績あり

## 注意事項

<特別な注意点、制約、トレードオフ>

例:
- `ensureConnected()` は最大5回リトライするため、テスト実行時間が若干増加する可能性がある
- `waitForLoadState("load")` は DOM のみの確認なので、JavaScript 実行完了を保証しない
- カーネル接続確認は `ensureConnected()` に依存するため、同関数のバグは影響大
```

## 品質基準

プランが以下を満たすことを確認:

- [ ] 根本原因が Issue の「調査メモ」と整合している
- [ ] 修正対象ファイルが全て特定されている（漏れがない）
- [ ] 各ファイルの変更前/変更後のコード例が具体的
- [ ] テスト戦略が明確（どのテストを修正/追加するか）
- [ ] 影響範囲が評価されている（直接影響・間接影響・リスク）
- [ ] 推定作業時間が妥当（5分〜60分程度）

## エラーハンドリング

### Issue ファイルが見つからない

```
❌ Issue ファイルが見つかりません: development_docs/issues/<slug>.md

以下を確認してください:
1. ファイル名が正しいか
2. ファイルが削除されていないか
```

→ オーケストレーターに報告し、次のバグへスキップ

### 修正方針が不明確

Issue に「修正方針」セクションがない、または複数案が並列で推奨が不明:

1. コードを調査して最も安全な修正方法を提案
2. プランに「推奨案が不明なため、以下の基準で選択」と記載
3. 選択基準:
   - 変更範囲が最小
   - テストカバレッジが最大
   - 既存パターンに従っている

### 関連ファイルが見つからない

Issue に記載されたファイルが見つからない場合:

1. Glob でファイル名を検索
2. Grep でコード内容を検索
3. 見つからない場合はプランに「ファイル移動の可能性あり」と記載
4. 手動確認を促す

## 成功基準

以下の条件を全て満たすプランを生成:

- [ ] 根本原因が明確に記載されている
- [ ] 修正対象ファイルが全て列挙されている
- [ ] 各ファイルの変更内容が具体的（コード例あり）
- [ ] テスト戦略が実行可能
- [ ] 影響範囲評価が合理的
- [ ] 推定作業時間が記載されている

## 注意事項

- プランは fix-agent が実装できるレベルまで具体化すること
- 「適宜修正」「必要に応じて」等の曖昧な表現は避ける
- コード例は実際のコードに基づくこと（推測で書かない）
- 複数ファイルにまたがる修正は優先度順に並べる
