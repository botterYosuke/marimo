## 良い点

1. **コアゲームループの完全動作確認**: E2E テストで SANDBOX_001→006→BRIDGE_001→003 の 9 スキルが自動取得できることが証明された。`bt.chart()` → `bt.buy()` → `bt.step()` → `bt.sell()` → `bt.reveal_data()` → `bt.get_stock_daily()` の全アクションが正しくスキルイベントを発火し、フロントエンド側で完了（completed）ステータスに更新される。これはゲームの中核品質として高く評価できる。

2. **TradingViewチャートの没入感**: 本格的なローソク足チャートがゲーム起動直後から表示され、視覚的な第一印象が非常に良い。投資ゲームとしての「本物らしさ」を演出している。

3. **スキルツリーのビジュアル設計**: React Flow を使用したグラフ表示は、スキルの依存関係が一目で把握でき、「次に何をすべきか」が視覚的に理解しやすい。カテゴリ別の左ボーダーカラーコーディング（緑=sandbox、青=bridge、赤=fail など）も直感的。ホバー時にエッジが金色でハイライトされる演出（`skill-tree-graph.tsx:87`）は前提条件の視認性を高めている。

4. **game_setup.py のユーザーフレンドリーな API**: `bt.buy()` 後に `mo.callout` で「**買い注文を出しました** — 7203 @ ¥X,XXX」を返す設計、`_format_step_summary()` による日付・資産・含み損益の整形表示など、Python コードの出力が学習者にとって親切。ガード節（ポジションなしで sell()、データなしで buy() を試みた場合の警告）も適切に実装されている。

5. **失敗スキルの設計哲学**: FAIL_001（含み損）・FAIL_002（損切り）・FAIL_003（破産）を「報酬対象」として設計しているのは、投資教育として優れた発想。「損切りはプロの証」「破産も大切な経験」のメッセージと helpContent の投資格言（「損小利大」など）が心理的安全性を高めている。

6. **HUD のリアルタイム更新**: ステータスバーに Time / Progress / Equity / Cash / Position / Trades が揃っており、BroadcastChannel を使ったリアルタイム更新は技術的に適切。今回 Position 表示が「0 shares」と正常化されたことで、基本的な情報表示の信頼性が向上した。Equity に `rewardCash` を加算する設計（`backtest-hud.tsx:117`）は、ゲーム内報酬とバックテスト資産を統合表示するユニークな演出。

7. **トースト通知のクリック連携**: `skill-reward-toast.tsx` のトーストをクリックするとスキルツリーダイアログが自動で開く設計は、「スキル取得 → ツリーを確認したい」という自然な行動フローに沿っていて優秀。

8. **helpContent の段階的開示**: 主要スキルには `helpContent` が設定されており、実際のコード例が丁寧に解説されている。「ノートブックに挿入」ボタン（unlocked 状態のみ表示）でコードを直接入力できる仕組みは、コード入力の摩擦を大幅に削減する。

9. **_check_graduations() による自動卒業スキル**: SANDBOX_001〜005 全完了で SANDBOX_006 が自動発火、BRIDGE_001 AND BRIDGE_002 完了で BRIDGE_003 が自動発火する仕組みは、プレイヤーに「自動で報酬が届いた」驚きをもたらし、良い演出になっている。

## 改善すべき点

1. **報酬表示がマイナス表記**: スキルツリーで「-30,000円」と表示されており、報酬なのか罰則なのか判断できない。`skill-data.ts:17` では `description: "+30,000円"` と正しく定義されているため、スキルノードの表示処理に問題がある。オンボーディング初日に混乱を生む致命的な UX 問題。

2. **再接続時スキルイベント消失（P1バグ）**: ページ再接続のたびに進捗がリセットされるため、ゲームとして最も基本的な「達成感の積み重ね」が機能しない。E2E テスト（backcast-integration.spec.ts）では `__testResetProgress()` でリセット後にクリーンな状態でテストしているため問題が顕在化しないが、実際のプレイヤー体験では常に発生する。

3. **BRIDGE_001 Python dedup バグ（BUG-NEW-3）**: `skill_events.py` の `_triggered_skills` セットがモジュールレベルで永続し、auto_instantiate による起動時スキルが残留する。テスト間・セッション間での状態汚染が発生し、`emitSkillViaPython("BRIDGE_001")` が no-op になる。ゲーム再プレイ時の信頼性を損なう。

4. **セル蓄積によるゲーム状態汚染**: プレイ中に作成したセルがノートブックに永続保存され、次回起動時に意図せずスキルが発火する。「ゲームリセット」の概念が欠如している。具体的には bt.buy() セル・BRIDGE_001 発火コード・重複 bt.chart() セルが蓄積された。

5. **AI Fix バナーがゲームモードで表示**: 「Fix generated / Showing fix / Accept / Reject」バナーが各セルに表示されており、ゲームの没入感を著しく損なう（P5 既知問題）。

6. **マイルストーン 35→50 の間隔が長すぎる**: 35スキルから次のマイルストーン（50スキル）まで 15 スキルを要する。フルモードの難易度 3 スキルが多い中盤で、プレイヤーのモチベーション維持が困難になる可能性がある。

7. **「マスター投資家」マイルストーンの不整合**: 全59スキルに対してマイルストーンは58スキル到達に設定されているが、残り1スキルを取得しても何の報酬もないため「やり遂げた感」が生まれない。全コンプリート演出が欠如している。

8. **helpContent の未設定スキルが多い**: SANDBOX_006、大半の SETUP・DATA・TRADE・CHART スキルに helpContent がない。特に「次のトラックへの扉」である SANDBOX_006「サンドボックス卒業」にヘルプがないことは、遷移点でのプレイヤー迷子を招く。各カテゴリの最初のスキルには最低限のオリエンテーションが必要。

9. **findCurrentTask() の表示精度**: `skill-tree-graph.tsx:21` の `findCurrentTask()` は「最初の unlocked スキル」にフォーカスする。複数のスキルが同時に unlocked になっている場合（例: SANDBOX_001 が unlocked かつ他も unlocked）、プレイヤーはどれに取り組むべきか分からない。優先度の視覚的な示唆が不足している。

## 具体的な改善提案（優先度順）

### 提案 1: 再接続時スキル進捗の永続化

- **現状**: Jotai atom は非永続化のため、ページ再読み込み・再接続のたびに進捗が 0 にリセットされる。スキルイベントは BroadcastChannel で届くが、atom がリセット済みのため無視される。`skill_events.py` の `_triggered_skills` は `load_progress()` で初期化されているが、フロントエンド側の永続化が追いついていない。
- **改善案**: スキル進捗を `localStorage` に保存し、atom の初期化時に `localStorage` から復元する（`atomWithStorage` への移行）。または `initProgressFromFileAtom` のバックエンド側読み込みを再接続後も確実に実行されるよう修正する。
- **期待効果**: プレイヤーの達成感が積み重なり、ゲームとして最低限機能するようになる。リプレイアビリティが大幅向上。
- **実装難易度**: 中（`atomWithStorage` への変更、または永続化フックの追加）

### 提案 2: BRIDGE_001 Python dedup バグの修正

- **現状**: `skill_events.py` の `_triggered_skills` セットがモジュールレベルの変数として永続するため、カーネル再起動なしのテスト再実行や次セッションでの再プレイ時に、既に `_triggered_skills` に登録済みのスキルが `emit_skill()` の先頭チェックで弾かれる。特に auto_instantiate が起動時にスキルを発火した場合に顕著。
- **改善案**: テスト用に `reset_triggered_skills()` 関数を追加して `_triggered_skills.clear()` を実行できるようにする。または `load_progress()` を毎回の `emit_skill()` 呼び出し時に参照するのではなく、「ゲームリセット API」を実装して `_triggered_skills` とファイルの両方をリセットする機能を提供する。
- **期待効果**: テストの再現性が向上し、再プレイ時のスキル発火が正しく機能する。
- **実装難易度**: 低〜中（`skill_events.py` への reset 関数追加 + `game_setup.py` / API エンドポイント側での呼び出し）

### 提案 3: 報酬表示のマイナス表記修正

- **現状**: スキルノードの報酬バッジで「-30,000円」とマイナス表示されている。`skill-data.ts` の `description` フィールドには「+30,000円」と正しく記載されているため、`skill-node.tsx` の `skill.reward[0].description` 表示処理か、スタイル・フォントの符号解釈に問題がある可能性が高い。
- **改善案**: `skill-node.tsx` の報酬バッジ表示部分を確認し、マイナス符号が付く経路を特定して修正する。数値表示の場合は `reward.value` を正として表示し、プラス符号を明示する（例: `+${reward.value.toLocaleString()}円`）。
- **期待効果**: 初回スキルツリー開封時の混乱がなくなり、報酬期待感が正しく伝わる。
- **実装難易度**: 低（表示ロジックの1箇所修正）

### 提案 4: ゲームセッションのクリーン起動機構

- **現状**: プレイ中に追加したセルが `backcast.py` に永続保存され、次回起動時に重複実行される。特に `BRIDGE_001` イベントを直接発火するコードが残留したケースが記録されている。`bt.buy()` や `bt.chart("7203")` が重複セルとして 2〜3 個存在する状態が確認された。
- **改善案**: (a) ゲームモード専用のノートブック「セル保護」機能を追加し、プレイセルとゲームセルを分離する。または (b) セッション開始時に「新しいゲームを始める」ボタンでノートブックをリセットするフローを実装する。短期的には `backcast.py` のセル数を監視し、閾値を超えたら警告を出す仕組みでも有効。
- **期待効果**: スキルの意図しない発火がなくなり、ゲームの公平性・再現性が確保される。
- **実装難易度**: 高（marimo のノートブック管理アーキテクチャに踏み込む必要あり）

### 提案 5: マイルストーン 35〜50 の間のサブマイルストーン追加

- **現状**: 35スキル（米国株ETF獲得）から 50スキル（Backcastエキスパート）まで 15 スキルの空白があり、難易度 3 のスキルが多いフルモード中盤で達成感が得られない長い空白期間となる。`skill-data.ts` の `milestones` 配列に 42 スキル相当のエントリが存在しない。
- **改善案**: 42スキル到達時に「中堅トレーダー」称号 +150,000円 のサブマイルストーンを追加する。または中盤スキル（IND_008 複合指標戦略、RISK_003 SL/TP 併用）完了時の演出を強化する。
- **期待効果**: 中盤の脱落率が下がり、フルコンプリートに向けたモチベーションが持続する。
- **実装難易度**: 低（`skill-data.ts` の `milestones` 配列への1エントリ追加）

### 提案 6: 59スキルコンプリートの特別報酬追加

- **現状**: マスター投資家マイルストーンは 58スキル到達で発動（`skill-data.ts:956`）。最後の 1 スキルを取得しても何の反応もない。`strategy_templates` の unlock が設定されているが、実際の機能が見当たらない。

- **期待効果**: 「ラストスキルを取りに行く」モチベーションが生まれ、全体のコンプリート率が向上する。

### 提案 7: AI Fix バナーのゲームモード非表示

## v3 追加発見（ソースコード直接レビュー）

### 報酬表示のマイナス問題 — 実際には発生しない可能性

`skill-node.tsx:133` を確認した結果、報酬バッジは `{skill.reward[0].description}` を直接レンダリングしており、`skill-data.ts:17` の `description: "+30,000円"` がそのまま表示されるはず。play-log で「-30,000円」と記録されたのは、旧バージョンの `skill-data.ts` に誤ったマイナス値が設定されていた可能性がある。現在のソースコードでは `description` に `"+"` プレフィックス付きで定義されており、表示バグは解消されている可能性が高い。要再確認。

### helpContent のマークダウン非レンダリング問題（新規）

`skill-detail-panel.tsx:185` で helpContent は `<pre className="whitespace-pre-wrap font-sans text-xs leading-relaxed">` でレンダリングされている。これはプレーンテキストとして表示されるため、helpContent 内の `## ようこそ`、`**太字**`、` \`\`\`python \`\`\` ` コードブロックが Markdown として描画されない。

- **問題**: `skill-data.ts` の helpContent は Markdown 記法で書かれているが、レンダラーが `<pre>` のため意図した表示にならない
- **改善案**: `<pre>` を `<ReactMarkdown>` または `mo.md()` 相当のレンダラーに変更する
- **実装難易度**: 低（`react-markdown` パッケージは既に frontend に存在する可能性が高い。差し替えのみ）

### HUD の Cash 表示に rewardCash を加算する設計の懸念（確認）

`backtest-hud.tsx:118,124` にて Equity と Cash の両方に `rewardCash` を加算している:

```tsx
value={formatYen(state.equity + rewardCash)}  // Equity
value={formatYen(state.cash + rewardCash)}     // Cash
```

Equity（総資産）に rewardCash を加算するのは合理的だが、Cash（現金残高）にも同じ rewardCash を加えると、「株式ポジションの含み益 = Equity - Cash」の計算が崩れる。プレイヤーが「Equity = Cash + 株式評価額」と解釈すると、数字が合わず混乱する可能性がある。設計意図の明確化、またはどちらか一方のみ加算への変更を検討すべき。

### findCurrentTask() の find() — 複数 unlocked 時の挙動確認

`skill-tree-graph.tsx:23` の `skills.find((s) => s.status === "unlocked")` は配列の先頭から検索するため、`skillDefinitions` 配列の定義順（SANDBOX_001 が先頭）で決まる。初期状態では SANDBOX_001 のみが unlocked のため問題なし。しかしゲーム中盤で複数スキルが同時 unlocked になると（例: SETUP_004 と SETUP_005 が共に SETUP_003 依存）、配列順で最初のスキルにのみフォーカスが当たる。これは既に v2 で指摘済みだが、ソースコードで確認した。

### game_setup.py の SANDBOX_001 発火タイミング — chart() 呼び出し時

`game_setup.py:74` にて `chart()` 関数内で `emit_skill("SANDBOX_001")` が発火される。これは帰納的に「チャートを表示したらマーケットへようこそ達成」を意味するが、helpContent（`skill-data.ts:22-37`）では「時間を進める」「株を買う」「チャートを見る」の 4 ステップが列挙されており、`bt.chart()` が最初のアクションであることが明示されていない。`bt.chart("7203")` を実行することで SANDBOX_001 が完了することを helpContent の冒頭に明示すべき。

### 詳細分析

#### 操作フロー

E2E フルラン結果（backcast-integration.spec.ts 全 6 PASS）により、完全プレイフローの技術的正確性は確認できた。`bt.chart("7203")` → `bt.buy()` → `bt.trades()` → `bt.sell()` → `bt.chart("7203")`（2 回目）→ 自動卒業（SANDBOX_006）→ `bt.reveal_data()` → `bt.get_stock_daily("7203")` → 自動卒業（BRIDGE_003）の 9 スキルが順次取得できる。

ただし `backcast.py` の Markdown セル（`## ようこそ、Backcastへ！`）には以下の順序で操作が説明されている:

```
1. bt.step() で次の日に進む
2. bt.buy() で株を買う
3. bt.step() で決済
4. bt.step() でチャートを確認
```

一方、SANDBOX_001 は `bt.chart("7203")` 呼び出しで発火する（`game_setup.py:74`）。ノートブックには既に `bt.chart("7203")` セルが初期配置されているため、プレイヤーは最初のセルを実行するだけで SANDBOX_001 を達成できるが、Markdown 説明にはそれが明示されていない。「このセルを実行すると最初の実績が解除されます」という一文があるとオンボーディングの達成感が大きく向上する。

#### エラーハンドリング

`guard-validation.spec.ts` の 3 件全失敗は、ゲームデザイン上の重大なギャップを示している。

- **テスト内容**: `bt.buy()` をデータなしで呼んだ際に「まず `bt.chart(...)` でチャートを表示してください」が表示されること、`bt.sell()` をポジションなしで呼んだ際に「保有中の株がありません」が表示されること
- **ソースコード上の実装**: `game_setup.py:85-95` にガードと `mo.callout` による警告は実装されている
- **考えられる原因**: グリッドレイアウトでのセル追加・実行フローで `mo.output.append()` の出力が期待するタイミング・場所に表示されない、またはテスト側のセレクター（`.cm-content` クリック → 警告テキスト待機）のタイムアウトが短い
- **ゲームデザインへの影響**: 初心者が正しい操作順序を学ぶ最初の機会が、エラーガードのフィードバックである。これが機能しない場合、プレイヤーはスタックトレースを見るかガード警告なしにクラッシュするという最悪の体験になる

`sell()` にも同様のガード（`if bt.position.size == 0:`）が実装されているが、Issue `sell-buy-no-guard-crash.md` では「ガードがない」と記述されており、ソースコードと乖離がある。これは Issue 作成時のソースコード確認漏れか、Issue 作成後にガードが追加された可能性がある。どちらの状態が最新かを確認し、ドキュメントの整合性を保つ必要がある。

#### スキルツリー設計

**BRIDGE_003 前提条件の Python/フロントエンド不整合**は、スキルツリー設計の一貫性という観点で評価すると重大な問題である。

- `skill_events.py`（Python 側）: `if "BRIDGE_002" in s:` — BRIDGE_001 確認なし
- `skill-data.ts`（フロントエンド側）: BRIDGE_003 の prerequisites に BRIDGE_002 のみ記載（この点も BRIDGE_001 を含む必要あり）

Python 側と TypeScript 側で前提条件定義が二重管理されており、両者が同期していない。スキル前提条件の「唯一の真実」をどこに置くかを設計方針として決め、片方から自動生成するアーキテクチャへの移行が長期的には望ましい。

**サンドボックス卒業設計の評価**: SANDBOX_001〜005 全完了 → SANDBOX_006 自動発火という設計は E2E で動作確認済みであり、ゲームデザインとしても「気づいたら卒業していた」驚きを与える良い演出である。一方で SANDBOX_005 の発火条件（`bt.chart("7203")` 2 回目呼び出し、かつ SANDBOX_003 + SANDBOX_004 完了済み）は `game_setup.py:75-76` で実装されているが、この条件がプレイヤーに一切説明されていない。「チャートをもう一度見てみよう」という行動を促すヒントが helpContent に必要。

**`findCurrentTask()` の複数 unlocked 時の UX**: v3 で指摘した問題が、ガード系スキルの並列 unlock で実際に影響する場面として確認できる。SANDBOX_002 完了後は SANDBOX_003（trades）と FAIL_001（含み損）が同時に unlocked になる可能性があるが、スキルツリーはどちらか一方にしかフォーカスしない。
